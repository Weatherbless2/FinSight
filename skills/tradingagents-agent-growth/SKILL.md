# TradingAgents 智能体成长

使用此技能把 TradingAgents 的面试问题转化为范围明确、可验证的工程工作。路线图是动态计划，不代表其中每项能力都已经实现。

默认用中文输出面向用户的讲解和面试答案；文件路径、代码标识符、命令和指标字段必须保持准确，不能为了中文化而翻译它们。

## 适用范围

当用户希望评估 TradingAgents 是否能回答智能体面试问题、选择或实现下一张学习工单、讲解项目架构，或更新路线图与面试笔记时使用。

不要用于泛化的智能体项目、简历改写，或只是在技术栈上与本项目重合的请求。

## 基本原则

0. 用户的总目标是：“总之现在的流程都是为了到时候面试的时候可以回答的上面试官反问的那些话语”。所有学习、测试和工程改造都必须服务于这个目标；每一张工单都必须对应一个明确的面试问题，并留下代码、测试、设计取舍和面试表达。
1. 在声称某项能力存在前，先检查当前仓库。每次评估和面试回答必须区分“已实现”“部分实现”“计划中”。
2. 除非用户要求重构，否则保持核心架构：固定的 LangGraph 工作流、局部“思考—行动—观察”式工具循环、中心化 `AgentState` 交接。
3. 金融安全边界必须由确定性规则控制。日期、来源、数值、数据结构和预算检查不能被大模型审查器推翻；审查器只能解释失败，不能放行不安全数据或执行。
4. 真实券商执行不在本技能的范围内。纸面交易模块在成为独立学习项目之前，必须先具备幂等、审批、审计和风控。
5. 不要为了看起来先进而增加检索增强生成或更多智能体角色。必须先说明证据来源、预期收益、成本和可测试的验收标准。

## 工作模式

### 评估或讲解

先阅读 [项目基线](references/project-baseline.md)，再核验当前仓库中的相关文件和测试。按以下顺序回答：

1. 项目当前实际做了什么。
2. 为什么采用该设计，以及取舍。
3. 缺少什么或有什么风险。
4. 最小的下一张工单，以及它能回答哪个面试问题。

讲解架构时，必须区分全局固定工作流与分析师局部的“智能体 -> `ToolNode` -> 智能体”循环。不能把项目称为完全自主智能体或已经具备检索增强生成的系统。

### 规划或重新排期

阅读 [路线图](references/roadmap.md)。除非存在明确阻塞或用户修改优先级，否则选择最早未完成的依赖项；P0/P1 工单优先于 P2 扩展。

每张建议工单必须写明：面试问题、已核验基线、变更范围、可能修改的文件、验收标准、测试、设计取舍和 30 秒面试答案。工单使用 Markdown 表格；仅当流程或依赖关系比表格更易理解时使用流程图。

当任务涉及财报、公告、知识库、RAG、PostgreSQL、pgvector 或 Redis 时，先阅读 [RAG 工单路线](references/rag-workorders.md)。该路线规定了 R-00 到 R-13 以及服务化 S-01/S-02 的依赖、Chunk 切分标准、评测指标和数据库职责；Redis 不能替代 PostgreSQL 的事实存储。

### 实现工单

1. 重读选中路线行，并在编辑前检查实际代码、配置和相邻测试。
2. 做最小兼容修改。除非工单明确要求改变，否则保持供应商降级、日期边界保护、结构化输出降级和检查点语义。
3. 添加聚焦且确定性的测试。优先使用模拟对象和测试样例，持续集成不依赖真实大模型或实时市场数据。
4. 运行受影响测试；若改动共享图、State、工具契约或 Provider 层，再运行更大范围测试。
5. 仅在代码和测试满足验收标准后更新路线状态；记录观察到的实际行为，不写愿景性结论。

### 过程、代码与量化结果

- 说明实现过程时要按实际链路展开：先定位文件和函数，再解释修改点、数据流、边界条件和验证方式，不能只给结论。
- 有代码改动时，给出能说明核心机制的关键代码片段；代码标识符保持原样，右侧或紧邻位置用中文解释关键行的作用。
- 测试结果尽量给真实量化指标：通过/失败/跳过数量、子测试数、耗时、覆盖的输入规模，以及改造前后可比较的延迟、调用次数、令牌或成本。明确区分“实测值”和“估算值”，没有数据时不要编造。
- 以快速推进主线为优先：普通工单只保留最小冒烟测试和关键边界测试；完整评测集、指标对比和回归报告集中在明确的评测工单中完成。
- 每张工单最后必须给一段简洁的完整总结，包含当前已实现能力、仍有限制、下一步和可直接复述的面试说法。
- 每张工单完成后必须明确告诉用户：做了哪些事情、每件事情的目的、实际结果和仍存在的限制；预期指标不能写成实测指标。

### 用户约定的工单输出格式

用户要求工单回答通俗、简洁，但不能只给结论。每张工单面向用户固定保留以下四部分：

1. **怎么实现**：按真实执行顺序说明定位了哪些文件、修改了什么、数据如何流转；给出最关键的代码片段，并在代码旁用中文解释作用。
2. **通俗解释**：用不依赖术语的语言说明这张工单解决了什么问题，以及它在 TradingAgents 业务链路中的作用。
3. **总结**：简要汇总修改文件、测试命令和实测结果、当前限制、下一张工单和可复述的面试说法。
4. **关键代码及详细中文注释**：只摘录本工单真正修改的核心函数，在代码行旁说明输入、处理、边界和输出；不要粘贴无关完整文件。

不要只输出“已完成”或愿景性结论；不要为了排版堆叠无关表格、流程图或重复说明。测试和限制仍必须真实记录，不能编造指标。

### 复核已完成工单

先检查缺陷、回归、不准确的实现声明、遗漏测试和不安全的金融行为。确认变更没有削弱未来数据与过期数据防护、有限循环、结构化输出校验、记忆与检查点的分离，以及密钥处理。最后给出当前工单已经支持的面试答案和仍存限制。

## 交付标准

每张完成工单都应留下实现、自动化测试、简短设计说明和 30 秒面试答案；对用户统一按“怎么实现、通俗解释、总结、关键代码及详细中文注释”四部分输出：

```text
怎么实现：按真实步骤、文件、关键代码和命令说明。
通俗解释：说明业务作用和设计取舍。
总结：说明修改、实测结果、限制、下一步和面试说法。
关键代码及详细中文注释：摘录核心函数并逐段解释。
```
