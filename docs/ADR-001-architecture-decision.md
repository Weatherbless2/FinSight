# ADR-001：TradingAgents 的智能体编排选型

## 状态

已采纳（2026-09-03）。这是当前 TradingAgents 的真实架构说明，不代表未来不能替换组件。

## 面试问题

为什么选择 LangChain、LangGraph 和固定工作流？为什么不使用一个大提示词、纯自主 Agent 或可视化编排平台？

## 当前基线

项目的实际链路是：

```text
用户输入
  -> AgentState 初始化
  -> 4 个分析师（每个分析师可局部调用工具）
  -> 看多/看空研究辩论
  -> 研究经理
  -> 交易员
  -> 激进/保守/中性风险辩论
  -> 组合经理
  -> 报告、决策记忆、可选 SQLite 检查点
```

分析师内部是局部循环：

```text
模型（决定是否调用工具）
  -> 条件路由
  -> ToolNode（执行白名单工具）
  -> 工具结果写入 messages
  -> 回到同一个分析师
```

整体仍然是固定顺序的 LangGraph `StateGraph`，不是完全自由的自主智能体。

## 决策一：使用 LangChain 封装模型和工具

代码证据位于 `tradingagents/agents/analysts/` 和
`tradingagents/graph/trading_graph.py`。

分析师会把工具绑定到模型：

```python
chain = prompt | llm.bind_tools(tools)  # 模型只能提出已绑定工具的调用请求
result = chain.invoke(state["messages"])  # 请求和分析上下文一起发送
```

`bind_tools` 不会直接执行工具，它只生成结构化的 `tool_calls`。实际执行由图中的 `ToolNode` 完成：

```python
"market": ToolNode([
    get_stock_data,                 # 行情数据
    get_indicators,                 # 技术指标
    get_verified_market_snapshot,   # 确定性验证快照
])
```

选择理由：

- 统一不同模型供应商的消息和工具调用协议。
- 可以复用 `AIMessage`、`ToolMessage`、`bind_tools` 等成熟接口。
- 工具白名单和结构化参数便于测试和安全控制。

## 决策二：使用 LangGraph 编排有状态流程

代码证据位于 `tradingagents/graph/setup.py`、
`tradingagents/graph/conditional_logic.py`、
`tradingagents/graph/propagation.py`。

```python
workflow = StateGraph(AgentState)  # 所有节点共享中心化状态
workflow.add_edge(START, plan.specs[0].agent_node)  # 固定起点
workflow.add_conditional_edges(  # 根据 tool_calls 选择工具或结束分析
    current_analyst,
    router,
    [current_tools, current_clear],
)
workflow.add_edge(current_tools, current_analyst)  # 工具结果回到原分析师
```

选择理由：

- `AgentState` 明确记录报告、辩论状态、消息和日期。
- 条件边可以表达工具循环、辩论轮换和终止条件。
- 检查点可以在节点边界保存和恢复状态。
- 图结构可回放、可测试、可审计，适合金融分析。

## 决策三：宏观采用固定工作流，局部保留智能体循环

固定工作流负责决定“先做什么、后做什么”：分析师、研究辩论、交易员、风险辩论和组合经理的顺序由代码定义。

局部智能体循环负责决定“当前节点需要哪些证据”：模型根据上下文选择工具，工具结果返回后再决定是否结束。

这样做的取舍是：

| 方面 | 得到的收益 | 付出的代价 |
|---|---|---|
| 可控性 | 节点顺序、工具白名单和轮数由代码限制 | 新增角色需要修改图结构 |
| 可审计性 | 每次状态和路由都能回放 | 需要维护状态字段和路径映射 |
| 灵活性 | 分析师可以按需调用不同工具 | 模型仍可能选择错误工具，需要校验和评测 |
| 金融安全 | 日期、来源、数值检查可由确定性代码控制 | 不能完全依靠模型自主规划 |
| 调试成本 | 节点边界清晰，容易定位失败 | 需要编写更多单元测试 |

## 为什么不使用其它方案

### 一个大提示词

适合一次性原型，但不适合作为当前主架构：

- 所有任务和上下文混在一起，容易超出窗口。
- 工具执行、重试和错误处理不容易形成明确边界。
- 很难只恢复失败节点，也难以统计单个节点的成本。
- 金融安全规则容易被模型文本覆盖。

### 纯自主 Agent 或 Plan-and-Execute

纯自主 Agent 的动态性更强，但路径、调用次数和成本更难预测。Plan-and-Execute 适合步骤经常变化的复杂任务，而 TradingAgents 的主流程已经相对稳定，额外规划会增加延迟和计划过期风险。

因此当前采用“固定工作流 + 局部循环”。以后如果实验表明分析师任务明显需要动态拆解，再单独引入计划节点并用回放指标验证收益。

### Dify 等可视化编排平台

可视化平台适合快速验证提示词和流程，但当前项目需要：

- Git 中可审查的代码变更。
- Python 类型、Pydantic 结构化输出和单元测试。
- 自定义供应商降级、日期边界和检查点语义。
- 在 WSL、持续集成和后续 FastAPI 服务中复用同一套代码。

所以当前不把可视化平台作为核心运行时；如果用于演示原型，也不能替代生产代码和测试。

## 实测结构指标

以下是 2026-09-03 在本地 WSL 环境的实测结果：

| 指标 | 实测值 | 说明 |
|---|---:|---|
| 默认图节点 | 20 | 4 个分析师各含分析、清理、工具 3 个节点，另有 8 个研究/交易/风险节点 |
| 条件路由 | 9 | 4 个分析师、2 个研究辩论、3 个风险辩论 |
| 条件目标 | 26 | 8 个分析师目标、6 个研究目标、12 个风险目标 |
| 默认工具数量 | 13 | 市场 3、情绪 1、新闻 5、基本面 4 |
| 全量自动化测试 | 585 通过 | 69 个子测试；2 个因可选依赖或密钥缺失跳过 |
| 全量测试耗时 | 254.33 秒 | 本地 `.venv`，不是线上性能承诺 |

节点数量通过模拟节点构造图统计，避免调用真实模型和市场接口；它反映图结构，不代表一次运行一定会访问全部节点。

## 验收方式

```bash
cd /root/projects/TradingAgents
.venv/bin/ruff check tradingagents/graph tests
.venv/bin/python -m pytest -q
```

验收重点：

- 图结构和代码中的节点名称一致。
- 工具调用能返回原分析师节点。
- 路由目标都在图中注册。
- 研究和风险辩论达到上限后进入终止节点。
- 空状态、异常路由不会静默生成错误报告。

## 30 秒面试答案

> 我们用 LangChain 统一模型和工具调用，用 LangGraph 的 `StateGraph` 管理共享状态和条件路由。宏观上采用固定工作流，保证分析师、研究辩论、交易员和风险复核的顺序可控、可审计；微观上分析师使用“模型决定调用工具、`ToolNode` 执行、结果回到模型”的局部循环，保留灵活性。相比一个大提示词或纯自主 Agent，这种设计更容易做状态恢复、轮数限制、工具白名单、成本统计和回归测试，代价是流程扩展需要修改代码。

## 当前边界和复查条件

- 当前不是完全自主多智能体系统。
- 当前没有把 Markdown 决策日志或 SQLite 检查点当作 RAG。
- 当前没有真实券商执行。
- 如果未来引入动态规划、可视化平台或并行分析师，必须用任务完成率、平均步数、延迟、令牌和成本做前后对比，再决定是否替换架构。
